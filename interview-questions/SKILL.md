# Interview Questions

按照“接收简历 → 总结简历 → 识别岗位 → 提取考察点 → 生成题目与参考答案 → 输出完整骨架 → 写入 Markdown 文件”的顺序完成。始终基于用户提供的原始简历，不持久化候选人信息。

## 接收简历

支持两种输入，优先使用已有材料，不同时要求多种：

- 粘贴文本：直接使用用户提供的简历全文。
- 本地 PDF：直接使用 Python 提取全文，按页保留段落结构，步骤见下文“PDF 提取”。

PDF 无法读取时说明原因，只请求完成任务所需的最小替代材料。不要自行 OCR，除非用户明确要求。

### PDF 提取

使用 Python 读取 PDF，所有操作仅限当前项目目录，禁止全局或系统级安装：

1. 在项目根目录创建项目级 venv：`python -m venv .venv`（已存在则跳过）。
2. 将 PDF 解析库装入该 venv，使用 `./.venv/bin/pip install`；不得使用 `--user`、全局 `pip install` 或系统 Python 环境。默认安装 `pypdf`。依赖安装属于环境变更，执行前先征得用户同意。
3. 使用技能自带的 [scripts/extract_pdf.py](scripts/extract_pdf.py) 按页提取文本，保留页序与段落（将 `<技能目录>` 和 `简历.pdf` 替换为实际路径）：

   ```bash
   ./.venv/bin/python <技能目录>/scripts/extract_pdf.py '简历.pdf'
   ```

4. 提取完成后直接进入“分析简历”，不保留中间文件。

材料充足时直接输出完整结果，不询问是否生成、是否继续。仅在简历内容不足以识别岗位方向时确认一次岗位方向。

手机号、身份证号、邮箱、具体住址等个人敏感信息不得出现在输出中。

## 分析简历

从原始简历提取：

- 姓名、教育背景、工作年限
- 岗位方向与当前定位
- 倒序的主要经历
- 2–4 个代表性项目及其目标、角色、技术栈和结果
- 核心技能栈与可量化成果
- 关键亮点、待澄清点和成长轨迹

从后端、前端、客户端、全栈、算法、数据、测试、运维、产品或其他方向中识别岗位方向，并引用原始简历中的具体依据。所有面试题仍以原始简历全文为依据，不以摘要替代原文。

### 学校与专业层次核验

对中国大陆高校，必须联网核验并在简历总结中输出学校层次和专业对应学科的全国水平：

- 学校层次：分别核验是否属于教育部公布的“985 工程”“211 工程”和当前一轮“双一流”建设高校，不得凭印象判断，也不得把历史上的 985/211 与当前“双一流”混为同一概念。
- 专业 / 学科水平：先将简历中的专业谨慎映射到对应一级学科，再优先查询教育部学位与研究生教育发展中心公开的最新一轮学科评估结果，输出评估档次、评价年份和该档次代表的全国相对水平；同时核验该学科是否属于当前一轮“双一流”建设学科。
- 如果本科专业无法唯一映射到一级学科，列出采用的映射并标记“映射待确认”；学科评估评价的是高校一级学科，不得表述为候选人所读本科专业的直接全国排名。
- 官方来源没有覆盖时，可补充有明确发布机构、年份和方法说明的全国专业排名，但必须标记为“非官方参考”；不同来源不得混合成一个自创排名。无法可靠核验时写“未查到可靠公开数据”，不得估算名次。

非中国大陆高校标记“985 / 211 / 双一流不适用”，不得强行换算为国内院校层次。每项结论都在正文中附来源链接和发布日期或评价年份。学校和学科层次可作为教育背景信号；除非岗位描述明确设置院校或专业门槛，否则不得仅凭学校标签或学科排名判定候选人的个人技术能力或是否进入面试。

### 面试建议判定

在岗位匹配度分析开头输出恰好两句话的“实力与能力总结”。第一句以“`<X 年>相关经验；`”开头，只写 2–4 项与目标岗位直接相关的具体能力，使用“技术 / 行动 / 解决的问题 / 可归因结果”的表达，例如写“使用 C# 对象池复用高频生成对象，减少运行时分配和 GC 压力”，不要写“具备扎实的 Unity/C# 能力”；工作年限无法确认时写“工作年限未提供”。第二句以“`年限匹配：低于预期 / 基本符合预期 / 高于预期；`”开头，对照目标岗位和工作年限说明能力证据是否达标，并指出最主要的证据缺口或待验证风险，不要复述“与岗位高度匹配”等结论。

总结只保留能够证明候选人个人能力的信息：奖项、比赛名次、参展经历、项目数量、产品 DAU 等内容，如果不能与候选人的具体职责、技术行动和结果建立直接因果关系，则不得写入；指标只有在能够归因于候选人的行动时才能作为能力证据。年级、在校身份、是否有正式实习等不是能力结论，只有在岗位描述明确将其设为硬性条件时，才放入面试建议的筛选依据。不得根据“创作者项目”“个人项目”或公司规模推断候选人缺乏工程规范和协作能力，只能如实写明简历未提供代码评审、版本协作、CI/CD 等相关证据。

技术名称只能证明接触范围，不能直接证明能力层级。量化成果必须尽量包含优化前后数据、测试场景或规模、候选人的具体行动和个人贡献；只有“稳定 60FPS”“完成包体瘦身”“使用 ECS”等表述而没有基线、适用场景、实现难点或归因信息时，只能视为弱证据，不得据此判定能力优秀。

岗位描述给出职级标准时优先使用该标准；未给出时按相关工作年限校准：不足 3 年重点判断能否在指导下完成明确任务并掌握基础原理；3–5 年应能独立负责模块、定位复杂问题、解释方案取舍、交付可量化结果并参与常规工程协作；6 年及以上还应体现系统或架构级设计、跨模块影响、线上稳定性或性能治理以及团队工程效能。处于年限区间上沿时按该区间的较高要求判断；重复使用相同技术或完成多个同类项目不能替代能力深度证据。

岗位描述存在时以其要求为准；未提供岗位描述时，以候选人简历体现的岗位方向和当前定位为准。综合判断核心能力匹配度、相关经历的深度与职责、成果证据、年限匹配度以及风险是否能通过面试验证，给出以下一种建议。不得仅因技术栈关键词匹配、项目数量多或工作年限长而给出“建议面试”：

- `建议面试`：存在明确的岗位相关经历或核心能力证据，剩余疑点适合在面试中验证。
- `谨慎面试`：具备部分相关证据，但关键能力、经历深度或个人贡献仍有明显缺口，需要结合招聘需求决定是否投入面试成本。
- `不建议面试`：岗位方向或核心要求明确不匹配、存在无法接受的硬性条件冲突，或简历缺少支持其目标岗位的基本证据。

无论结论为何，都分别列出 2–4 条“为什么该面试”和“为什么不该面试”，每条引用简历或岗位描述中的具体依据，并说明最终结论由哪些关键证据决定。简历未提供的信息只能标记为待确认；可以将关键证据缺失作为筛选风险，但不得据此断言候选人不具备相应能力。

## 生成题目

使用以下五个分类，顺序固定，不得合并、重命名或替换为自由标题：

- `### 3.1 技术基础`
- `### 3.2 技术进阶`
- `### 3.3 项目深挖`
- `### 3.4 场景 / 设计`
- `### 3.5 软素质`

题目必须同时覆盖目标岗位的通用能力和原始简历体现的能力，不得全部围绕简历项目定制。技术基础题考查岗位核心知识和基本原理；技术进阶题考查机制、性能、边界和取舍。岗位通用题可以考查简历未提及、但属于目标岗位核心知识的内容，题干不得暗示候选人使用过该技术，也不得选择与目标岗位无关的冷门知识。

默认 3 道技术基础题中，2 道为岗位通用题、1 道结合简历技能；默认 3 道技术进阶题中，1 道为岗位通用题、2 道结合简历技能。题量发生变化时，技术基础和技术进阶只要仍有题目，各自至少保留 1 道岗位通用题。

生成题目前先根据目标岗位职级和相关工作年限确定考察层级；岗位描述明确职级时优先按岗位要求，否则按以下标准调整同一知识点的问法和答案深度：

- 实习生 / 应届生：重点考查基础概念、运行流程、简单实现、常见错误、调试思路和学习过程，不预设其具备生产环境架构或企业协作经验。
- 1–2 年：重点考查独立完成功能、常见故障定位、代码质量、工具使用和基本方案取舍。
- 3–5 年：重点考查模块设计、复杂问题根因定位、性能数据与验证方法、异常边界、可维护性、线上问题和工程协作；5 年候选人按该层级上沿提问，不能只问概念定义或 API 用法。
- 6 年及以上：重点考查系统与架构设计、跨模块约束、规模化瓶颈、稳定性治理、长期演进、技术决策和团队工程效能。

题目难度必须与经验层级匹配，但不得只因工作年限预设候选人已经掌握某项技术。对中高级候选人，题干应要求给出具体决策依据、测量方法、失败模式和取舍；对实习生或应届生，应允许使用课程、个人项目或假设场景说明思路。参考答案也必须匹配同一层级，不能用初级答案作为中高级题目的标准答案。

项目题点名具体项目并追问角色、方案、难点、数据和复盘；场景题结合候选人经历；软素质题引用具体经历。不得编造简历中未出现的数据、项目或候选人经历。

每道题使用以下格式：

```markdown
- [ ] **题目：** …

  **考点：** …

  **参考答案：** …
```

每道题、考点和参考答案必须放在同一个题目块内，并使用空行和加粗标签分隔；不得压缩到同一行。

每道题都必须给出简洁、可核验的参考答案要点，并完整回应题目中的每个子问题。

技术题的答案必须覆盖“实现或运行流程 → 底层机制 → 影响结果 → 边界与取舍”的因果链，解释问题为何发生、消耗了什么资源、最终造成哪些可观察影响，不得只写“提升性能”“减少卡顿”等表层结论。例如涉及 GC 时，应说明短生命周期对象的频繁分配如何增加托管堆压力并触发垃圾回收，标记、清扫或压缩等阶段如何消耗 CPU、引入暂停或帧时间抖动，并进一步影响吞吐、延迟和内存峰值；具体行为依赖运行时实现时，要明确区分通用原理与特定运行时结论。

项目深挖、场景 / 设计和软素质题的答案说明优秀回答应覆盖的要点，不得代替候选人编造简历中未提供的经历、数据或结论。不要输出评分标准、追问清单、编程笔试或限时作业，除非用户明确要求。

### 数量与配额

默认按 3 分钟一题生成 10 题，对应 30 分钟：

| 分类 | 题数 |
| --- | ---: |
| 3.1 技术基础 | 3 |
| 3.2 技术进阶 | 3 |
| 3.3 项目深挖 | 2 |
| 3.4 场景 / 设计 | 1 |
| 3.5 软素质 | 1 |

3.3 默认覆盖两个不同项目。用户指定总时长时，题目数为总分钟数除以单题分钟数并四舍五入；用户指定单题时长时使用该时长，否则仍按 3 分钟。

题目多于 10 道时，按 3.1、3.2、3.3 的顺序循环增加。题目少于 10 道时，按 3.1、3.2、3.3 的顺序循环减少；3.1、3.4 和 3.5 不得少于 1 道。配额用满即停。

## 写入文件

在回复中输出完整骨架后，将同一份骨架原样写入 Markdown 文件：

- 文件名：`面试题-<候选人姓名或“未知”>-<岗位方向>-<YYYYMMDD>.md`，字段取值与一级标题保持一致。
- 写入当前工作目录；文件已存在则覆盖。
- 文件内容与回复中的骨架逐字一致，不得增删章节、调整顺序或重新排版。
- 写入完成后在回复末尾单行给出文件相对路径，不附加额外说明，不询问后续操作。
