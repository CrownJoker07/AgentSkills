# Interview Questions

按照“接收简历 → 总结简历 → 识别岗位 → 提取考察点 → 生成题目 → 输出完整骨架”的顺序完成。始终基于用户提供的原始简历，不持久化候选人信息。

## 接收简历

支持两种输入，优先使用已有材料，不同时要求多种：

- 粘贴文本：直接使用用户提供的简历全文。
- 本地 PDF：使用当前环境可用的 PDF 读取工具按页提取全文并保留段落结构。

PDF 无法读取时说明原因，只请求完成任务所需的最小替代材料。不要自行 OCR，除非用户明确要求。

材料充足时直接输出完整结果，不询问是否生成、是否继续。仅在简历内容不足以识别岗位方向时确认一次岗位方向。

手机号、身份证号、邮箱、具体住址等个人敏感信息不得出现在输出中。

## 分析简历

从原始简历提取：

- 姓名、教育背景、工作年限
- 岗位方向与当前定位
- 倒序的主要经历
- 2–4 个代表性项目及其目标、角色、技术栈和结果
- 核心技能栈与可量化成果
- 关键亮点、待澄清点和成长轨迹

从后端、前端、客户端、全栈、算法、数据、测试、运维、产品或其他方向中识别岗位方向，并引用原始简历中的具体依据。所有面试题仍以原始简历全文为依据，不以摘要替代原文。

## 生成题目

使用以下六个分类，顺序固定，不得合并、重命名或替换为自由标题：

- `### 4.1 动机与职业规划`
- `### 4.2 技术基础`
- `### 4.3 技术进阶`
- `### 4.4 项目深挖`
- `### 4.5 场景 / 设计`
- `### 4.6 软素质`

题目必须贴合原始简历：基础题考查核心技能原理；进阶题考查机制、性能、边界和取舍；项目题点名具体项目并追问角色、方案、难点、数据和复盘；场景题结合候选人经历；软素质题引用具体经历。不要编造简历中未出现的技术、数据或项目。

每道题使用以下格式：

```markdown
- [ ] 题目
  考点：…
```

必问题在 `- [ ] ` 后紧跟 `★`。不要输出参考答案、评分标准、追问清单、编程笔试或限时作业，除非用户明确要求。

### 必问清单

以下题目必须原样放在 4.1 的第一题：

```markdown
- [ ] ★如果你入职后参与的项目方向与你最初预期不一致，你会如何衡量是否继续投入？
  考点：职业成熟度、预期管理、在项目与个人偏好冲突时的取舍与自我驱动
```

### 数量与配额

默认按 3 分钟一题生成 10 题，对应 30 分钟：

| 分类 | 题数 |
| --- | ---: |
| 4.1 动机与职业规划 | 2 |
| 4.2 技术基础 | 2 |
| 4.3 技术进阶 | 2 |
| 4.4 项目深挖 | 2 |
| 4.5 场景 / 设计 | 1 |
| 4.6 软素质 | 1 |

4.4 默认覆盖两个不同项目。用户指定总时长时，题目数为总分钟数除以单题分钟数并四舍五入；用户指定单题时长时使用该时长，否则仍按 3 分钟。

题目多于 10 道时，按 4.2、4.3、4.4 的顺序循环增加。题目少于 10 道时，按 4.2、4.3、4.4 的顺序循环减少；4.1 不得少于 1 道，4.5 和 4.6 不得少于 1 道。配额用满即停。

## 输出骨架

固定使用以下结构和顺序。信息不足时在对应条目写明“简历未提供”，不得省略章节：

```markdown
# 面试题 - <候选人姓名或“未知”> - <岗位方向> - <YYYYMMDD>

> 面试时长：<N 分钟>（<M 题 × 每题分钟数>）

## 一、候选人基本信息
- 姓名、学校、专业、年级 / 届别
- 期望岗位、期望城市、实习时间
- 工作年限（在校 / 在职 / 离职）

## 二、简历总结
- 岗位方向与当前定位
- 主要经历（倒序）
- 代表性项目（2–4 个）
- 核心技能栈
- 可量化成果

## 三、岗位匹配度分析
- 岗位方向推断依据（引用原始简历）
- 关键亮点（3–5 条）
- 潜在风险点（2–4 条）
- 建议重点考察的方向（2–4 条）

## 五、面试官备注
- 信息不足的项目
- 需要确认的方向
- 基于风险点的 2–3 条建议追问方向
```
