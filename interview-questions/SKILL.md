# Interview Questions

按照“接收简历 → 总结简历 → 识别岗位 → 读取参考题库并提取考察点 → 生成题目与参考答案 → 输出完整骨架 → 写入 Markdown 文件”的顺序完成。始终基于用户提供的原始简历，不持久化候选人信息。

## 硬性规则（优先级最高）

与其他说明冲突时以本节为准。

1. **量化即证据。** 一条描述只有同时具备「具体技术机制 + 候选人自己的动作 + 改造前后的数据或规模」三要素才算能力证据。缺任一项一律按不成立处理（视为夸大或虚构），不得写入“能力”行、不得作为“该面”依据，只能在“待确认”里列为需核验的疑点。
2. **名词与动词不算证据。** 技术栈罗列只证明听说过，`主导 / 负责 / 搭建 / 参与 / 优化` 只证明自称做了；`显著降低 / 大幅提升 / 提效 200%` 这类无基线、无测量口径、无场景的数字或形容词不产生证据分，按“弱证据”或“无证据”处理。
3. **格式只有骨架里的表格与固定条目名。** 禁止把“简历总结”写成`- **标签：** 长句`的项目符号段，禁止在表格外补写散文段；每行或每格最多 3 项、40 字内，信息多就拆成骨架已有的多行（每段经历一行、每个维度一行）。
4. **超限只能删信息。** 不得为了塞进长度上限而改成密排长行、缩并句子、换行续写同一事实，或把表格内容挪到表格外说明。
5. **判定过程不外露。** 证据分级、年限门槛、配额计算、技术栈迁移只在内部完成，输出中不出现规则原文与推导文字。

## 接收简历

支持两种输入，优先使用已有材料，不同时要求多种：

- 粘贴文本：直接使用用户提供的简历全文。
- 本地 PDF：使用 Python 提取全文，按页保留段落结构，步骤见下文“PDF 提取”；不得因为“能提取到字符”就认为内容已取到，需检查脚本的页标记。文本层为空或是水印 / 重复噪声（招聘平台导出的图片型简历常见）时，脚本自动回退到 OCR，不需要额外材料。

PDF 完全无法读取（加密、损坏，或提取与 OCR 后都没有内容）时说明原因，只请求完成任务所需的最小替代材料，例如文字版简历。

### PDF 提取

所有操作仅限当前项目目录，禁止全局或系统级安装：

1. 在项目根目录创建项目级 venv：`python -m venv .venv`（已存在则跳过）。
2. 用 `./.venv/bin/pip install` 安装依赖，不得使用 `--user`、全局 `pip install` 或系统 Python 环境。默认只需 `pypdf`；图片型或扫描版简历额外需要 `pymupdf ocrmac`（OCR 调用 macOS 自带 Vision 框架，不需要系统级依赖）。依赖安装属于环境变更，执行前征得用户同意，并把本次需要的依赖一次问清。
3. 运行技能自带的 [scripts/extract_pdf.py](scripts/extract_pdf.py)（将 `<技能目录>` 和 `简历.pdf` 替换为实际路径）：

   ```bash
   ./.venv/bin/python <技能目录>/scripts/extract_pdf.py '简历.pdf'
   ```

   脚本按页输出文本；某页去重后有效文字少于 40 字、或字符种类少于 60（重复水印串的特征）时，判定该页不可读并自动渲染做 OCR，页头标注 `(ocr, confidence …)`，整页识别不出内容时标注 `(ocr, no content)`，临时图片自动清理。
4. 非 macOS 环境或 OCR 依赖缺失时脚本会报错退出；此时请求文字版简历，不自行换用其他 OCR 方案，除非用户同意。
5. 提取完成后直接进入“分析简历”，不保留中间文件。

### OCR 简历的可信度

- OCR 文本按原样作为简历依据，不猜测、不“修正”识别结果；数字、日期、公司名、技术名词最容易出错。
- 工作年限、量化指标等关键信息只出现在 OCR 页且只出现一次时，在“待确认”条目注明来自图片识别、需面试核对。
- 置信度偏低、标为 `no content` 或明显乱码的页，在“待确认”写明“第 N 页图片识别质量差，内容可能不完整”，不得据其给出能力结论。
- 不在输出里粘贴 OCR 原文或展示提取过程，仍按骨架只写有依据的核心信息。

材料充足时直接输出完整结果，不询问是否生成、是否继续。仅在简历内容不足以识别岗位方向时确认一次岗位方向。

手机号、身份证号、邮箱、具体住址等个人敏感信息不得出现在输出中。

## 分析简历

从原始简历提取以下信息用于判定，输出时逐条填入骨架表格的对应单元格，一格一条，不在简历总结里展开分析过程：

- 姓名、教育背景、工作年限与在职状态
- 岗位方向与当前定位
- 倒序的主要经历，以及 2–4 个代表性项目的角色、技术动作和可归因结果
- 核心技能栈，以及每条成果是否具备“机制 + 动作 + 数据”三要素；缺数据时在“经历”表标“(无量化)”
- 关键亮点与待澄清点

从后端、前端、客户端、全栈、算法、数据、测试、运维、产品或其他方向中识别岗位方向，并引用原始简历中的具体依据；该依据用于内部判定，输出时只体现在“方向 / 定位”单元格，不单独成条。所有面试题仍以原始简历全文为依据，不以摘要替代原文。

### 学校与专业核验

教育背景只输出招聘筛选需要的信息，填入“简历总结”表格的“姓名 / 学历”与“专业相关性”两行，不展开一级学科映射、学科评估档次、双一流建设学科或多套榜单比较：

- 中国大陆高校：联网核验是否为 985、211、当前一轮双一流建设高校，并查询一项最新、主流且有明确年份的全国院校排名。用一句话写清“学校大致怎么样、全国排名、985 / 211 / 双一流情况”，附来源和年份。排名来源未收录该校时写“该榜单未收录”，不得估算名次或改用多套榜单拼凑结论。
- 专业：只说明专业名称及其与目标岗位是否直接相关；除非岗位描述明确设置专业或学科等级门槛，否则不查询专业排名，不做本科专业到研究生一级学科的映射。
- 非中国大陆高校：标记“985 / 211 / 双一流不适用”，使用一项适合该地区的主流院校排名简要说明学校情况。

院校层次和排名只作为教育背景信号；除非岗位描述明确设置院校或专业门槛，否则不得据此判定候选人的个人技术能力或是否进入面试。

### 面试建议判定

按骨架“建议”条目输出两行，不写推导过程。“能力”行以“`<X 年>相关经验；`”开头，只写 2–3 项与目标岗位直接相关的具体能力，使用“技术 / 行动 / 解决的问题 / 可归因结果”的表达，例如写“使用 C# 对象池复用高频生成对象，减少运行时分配和 GC 压力”，不要写“具备扎实的 Unity/C# 能力”；工作年限无法确认时写“工作年限未提供”。“结论”行以“`年限匹配：低于预期 / 基本符合预期 / 高于预期；建议面试 / 谨慎面试 / 不建议面试；`”开头，给出结论并指出最主要的证据缺口，不复述“与岗位高度匹配”等表述，也不再单独写“最终结论的关键证据”。

总结只保留能够证明候选人个人能力的信息：奖项、比赛名次、参展经历、项目数量、产品 DAU 等内容，如果不能与候选人的具体职责、技术行动和结果建立直接因果关系，则不得写入；指标只有在能归因于候选人行动、且有改造前后数值与测量场景时才能作为能力证据，只有单点数字（“DAU 100 万”“10+ 款上线”）不算。
年级、在校身份、是否有正式实习等不是能力结论，只有在岗位描述明确将其设为硬性条件时，才放入面试建议的筛选依据。不得根据“创作者项目”“个人项目”或公司规模推断候选人缺乏工程规范和协作能力，只能如实写明简历未提供代码评审、版本协作、CI/CD 等相关证据。

技术名称只能证明接触范围，不能直接证明能力层级。每条经历与项目按三要素拆解：技术机制（用了什么、为什么这样实现）、个人动作（本人做了哪个决定或改动）、量化结果（改造前后的数值、规模或线上事实）。三要素齐全的才写成“技术 / 行动 / 解决的问题 / 可归因结果”；只有“做了某功能”“用了某方案”而无机制与数据的，按硬性规则 1 处理，视为不实陈述候选，不作为能力证据，并在“待确认”注明“无量化，需核验真实性”。简历通篇没有任何前后数据时，“结果闭环”直接判“无”。

先对每项能力证据分级；同一内容在技能、工作经历和项目经历中重复出现时只计算一次：

- `强证据`：三要素齐全，作用范围明确，给出可归因的前后指标或线上结果。
- `中证据`：有具体机制、模块边界或故障定位过程，能确认本人实际动手，但没有前后数据。只支持“做过”，不支持“做得好”。
- `弱证据`：只有技术名词堆叠、形容词化结果（`显著降低`、`提效 200%`）或自我评价，无机制、无基线、无个人决策。
- `无证据`：只有“负责 / 参与 + 做了什么”的职能描述，既无机制也无数据；或简历未提及。

按“独立负责、技术深度、结果闭环、生产与工程协作”四个维度各占一行填入“证据”表格，只写等级和一句最直接的简历依据，不复述分级定义、不加额外说明。岗位描述给出职级标准时优先使用该标准；未给出时按相关工作年限校准：

- 不足 3 年：重点判断能否在指导下完成明确任务并掌握基础原理，不强制要求架构或完整量化闭环。
- 3–4 年：应在独立负责和技术深度两个维度达到中证据及以上，并在结果闭环或工程协作中至少一项达到中证据及以上。
- 5 年：按成熟工程师标准判断；只有四个维度中至少三个达到中证据及以上、至少一个达到强证据，且“独立负责”以及“技术深度 / 结果闭环”至少一项不是弱证据时，才能判为“基本符合预期”。不满足该门槛即判为“低于预期”，不能因为技术栈覆盖面广或项目数量多而放宽。
- 6 年及以上：除满足 5 年门槛外，还应在系统或架构级设计、跨模块影响、线上稳定性或性能治理、团队工程效能中体现至少两项中证据及以上；否则不得判为“基本符合预期”。

5 年及以上候选人若“结果闭环”为弱或无（即全篇没有任何可归因的前后数据），结论不得高于“谨慎面试”；此时简历中的倍率与百分比宣称只能作为待核验疑点，不得当作成果证据。

“高于预期”要求超过对应年限门槛，并有多个强证据证明更高层级的职责和结果。重复使用相同技术、完成多个同类项目或罗列多个优化动作不能替代能力深度。材料不足时评价的是“简历证据低于预期”，不得直接断言候选人的真实能力差。

“能力”行与“该面”只能引用三要素齐全或中证据以上的条目；弱证据与无证据条目一律不得出现在“能力”行和“该面”，只能落到“不该面”（写缺哪一要素）或“待确认”（写需核验什么）。

岗位描述存在时以其要求为准；未提供岗位描述时，以候选人简历体现的岗位方向和当前定位为准。综合判断核心能力匹配度、相关经历的深度与职责、成果证据、年限匹配度以及风险是否能通过面试验证，给出以下一种建议。不得仅因技术栈关键词匹配、项目数量多或工作年限长而给出“建议面试”：

- `建议面试`：存在明确的岗位相关经历或核心能力证据，剩余疑点适合在面试中验证。
- `谨慎面试`：具备部分相关证据，但关键能力、经历深度或个人贡献仍有明显缺口，需要结合招聘需求决定是否投入面试成本。
- `不建议面试`：岗位方向或核心要求明确不匹配、存在无法接受的硬性条件冲突，或简历缺少支持其目标岗位的基本证据。

年限匹配为“低于预期”时不得给出“建议面试”：如果岗位允许降级录用且关键缺口可能通过面试澄清，可给出“谨慎面试”；否则给出“不建议面试”。年限匹配达到“基本符合预期”也不自动等于建议面试，仍需结合岗位核心要求和硬性条件判断。

无论结论为何，都分别列出 2–3 条“该面”和“不该面”，每条一行、只讲一个依据。原先分散的“信息不足的项目”“需要确认的方向”“建议追问方向”合并为“待确认”2–4 条，每条写成不超过 25 字的确认项短语（如“红点重构的前后指标与代码归属”），不写完整问句，也不复述“不该面”已说明的理由；简历中每一处无量化的成果宣称都要在其中占一条。简历未提供的信息只能标记为待确认；可以将关键证据缺失作为筛选风险，但不得据此断言候选人不具备相应能力。对无量化宣称按不采信处理是对其陈述可信度的判断，不等于断言其真实能力差，两者在输出中都不写成对个人品质的指控。

## 参考题库

识别出岗位方向和主力技术栈后，只读取本次面试相关的文件（路径相对本技能目录）：

- 主力语言为 C# / .NET，或岗位为 .NET 后端：[references/csharp-dotnet.md](references/csharp-dotnet.md)
- Unity、游戏客户端、引擎、图形、玩法程序：[references/unity-game.md](references/unity-game.md)
- 6 年及以上候选人、架构师 / 技术负责人、平台或系统设计岗位：[references/architecture.md](references/architecture.md)
- 方向同时命中多个文件时全部读取（Unity 客户端岗位通常同时读 C# 与 Unity 两份）。
- 需要在题目或参考答案中核对具体机制、生效条件与版本边界时，用 [references/SOURCES.md](references/SOURCES.md) 解析参考题库正文中的 `[S001]`、`[S010]` 等编号，指向官方出处。
- 面试控场技巧与岗位方向无关，每次都必须读取：[references/interview-control.md](references/interview-control.md)。用于在“控场”条目输出防止被候选人带着跑的提示。

参考题库只提供考点范围、参考答案的深度基准和追问方向，属于岗位通用知识，不是候选人的经历证据。不得因为某项知识点在参考题库里，就认定候选人掌握它或应当掌握到某一程度；也不得把参考题库的题干直接照搬。

选题顺序：先在参考题库的考点地图中筛出与目标岗位核心能力相关、且与简历证据或岗位描述有关的知识点，再按候选人实际使用的版本、渲染管线、运行时和项目场景改写题干与答案。参考题库覆盖但目标岗位不需要的内容不占题目配额；目标岗位核心知识不在参考题库里时照常出题。

版本敏感结论（GC 行为与堆结构、合批与 SRP Batcher 生效条件、协程与异步任务的恢复时机、中间件顺序、AOT / IL2CPP 限制等）必须在参考答案中写明所属运行时、渲染管线或版本前提，区分“通用原理 / 主流实现 / 特定版本行为”，不得写成普适保证。

候选人没有实际使用证据的专属机制，按“目标技术栈与候选人技术栈不一致”规则迁移考点；`references/unity-game.md` 的“跨引擎迁移问法”一节给出可迁移的通用能力清单。

`[Sxxx]` 编号与来源清单只用于内部校准，不出现在回复和写入的 Markdown 文件中。

参考题库是本技能针对常见技术栈的可选扩展，不改变五个固定分类、题量配额和输出骨架。目标岗位不属于 C# / .NET、Unity 或架构方向时，不得把参考题库中的术语、示例场景或考点带进题目与参考答案；其他方向的候选人按其自身技术栈和岗位描述出题。`references/interview-control.md` 是例外：它规定控场手法，与技术栈无关，任何方向的面试都适用。

## 生成题目

使用以下五个分类，顺序固定，不得合并、重命名或替换为自由标题：

- `### 2.1 技术基础`
- `### 2.2 技术进阶`
- `### 2.3 项目深挖`
- `### 2.4 场景 / 设计`
- `### 2.5 软素质`

题目必须同时覆盖目标岗位的通用能力和原始简历体现的能力，不得全部围绕简历项目定制。技术基础题考查岗位核心知识和基本原理；技术进阶题考查机制、性能、边界和取舍。岗位通用题可以考查简历未提及、但属于目标岗位核心知识的内容，题干不得暗示候选人使用过该技术，也不得选择与目标岗位无关的冷门知识。

技术基础题以岗位通用题为主；技术进阶题至少保留 1 道岗位通用题，其余结合简历技能。技术基础和技术进阶只要仍有题目，各自至少保留 1 道岗位通用题。

岗位通用题优先从参考题库的考点地图中选取：C# / .NET 见 `references/csharp-dotnet.md` §1，Unity 与游戏客户端见 `references/unity-game.md` §1–§8，架构与系统设计见 `references/architecture.md` §3–§6。选定知识点后再按候选人实际使用的版本、管线和项目场景改写题干。

### 目标技术栈与候选人技术栈不一致

生成题目前先把目标岗位的特定技术栈与候选人简历中有实际使用证据的技术栈分开。简历未提及某项技术，或仅写“了解 / 学习过 / 做过练习 Demo”而没有项目或工作证据时，不得把该技术的专属 API、生命周期、资源系统、渲染管线或内部机制作为正式题目的主要考点。

当岗位要求的引擎、框架或语言与候选人熟悉的技术栈不一致时：

- 技术基础、技术进阶和性能优化优先使用候选人熟悉的引擎、框架或语言提问，考察可迁移的底层能力。例如将“Unity 性能优化”改为“你熟悉的游戏引擎中的性能优化”，要求候选人结合真实工具、指标、定位过程和优化结果作答。
- 将引擎专属知识抽象为跨引擎能力，例如游戏循环、资源生命周期、渲染批次、内存与 GC、事件系统、网络同步、调试和性能分析；参考答案先给通用原理，再允许候选人用其熟悉的技术栈说明实现。
- 不用目标技术栈冷知识筛掉候选人。对目标技术栈的现有接触程度只在“待确认”条目中快速确认，不占默认正式题目配额。
- 10 道题中安排 2 道技术迁移与学习能力题：一道放在“场景 / 设计”，考察如何把已有能力映射到目标技术栈并完成实际任务；一道放在“软素质”，要求用过去快速学习新技术的真实经历说明学习方法、验证方式、用时和结果。总题数变化时仍优先保留这两类考察各 1 道。
- 参考答案不得要求候选人直接给出其未实际使用技术的完整实现细节；应评价其基础能力是否扎实、迁移差距识别是否准确、学习计划是否可执行，以及能否通过小任务和可观测结果证明已经上手。

### 主力编程语言深度题

对 3 年及以上候选人，必须在“技术进阶”中安排 1 道高难度的主力编程语言深度题，用于验证其经验是否只停留在业务 API 使用层面：

- 主力语言必须有简历中的生产使用证据；目标岗位使用另一种语言时，仍考候选人的主力语言，不得改考其没有实际经验的目标语言。
- 题目必须结合真实故障或性能场景，考查该语言的运行时、对象与内存模型、垃圾回收、并发模型、调用或执行机制中的相关底层原理，并要求说明可观察现象、定位方法和方案取舍。
- 难度应来自机制之间的因果关系和工程判断，不得用冷门语法、偏门标准库 API、记忆实现版本细节或语言谜题充当高难度。
- 只选择与候选人经历及岗位有实际关系的一条问题链，不得把多个互不相关的底层知识堆进同一道题。参考答案应区分语言规范、主流运行时实现和特定版本行为，不能把实现细节错误表述为语言保证。
- 该题用于识别技术深度上限。候选人不必背出全部术语，但应能从现象推导原因并给出验证方法；如果回答只停留在语法或 API 层面，应作为其对应年限技术深度不足的证据。

例如，主力语言为 Python 时，可以用长期运行的游戏客户端出现帧时间尖峰或内存增长作为场景，考查 CPython 引用计数与循环垃圾回收、对象生命周期、GIL 对并发方案的影响，以及如何使用实际数据定位问题；不要单独考元类写法或冷门语法输出结果。

主力语言为 C# 时，可直接采用 `references/csharp-dotnet.md` §2（GC 与内存）或 §3（`async` 与线程）的问题链模板，把场景替换为候选人简历中的真实系统，并按简历提供的数据改写；Unity 引擎侧的分配与生命周期机制见 `references/unity-game.md` §1、§3、§4，用于交叉验证其优化结论是否成立。

生成题目前先根据目标岗位职级和相关工作年限确定考察层级；岗位描述明确职级时优先按岗位要求，否则按以下标准调整同一知识点的问法和答案深度：

- 实习生 / 应届生：重点考查基础概念、运行流程、简单实现、常见错误、调试思路和学习过程，不预设其具备生产环境架构或企业协作经验。
- 1–2 年：重点考查独立完成功能、常见故障定位、代码质量、工具使用和基本方案取舍。
- 3–5 年：重点考查模块设计、复杂问题根因定位、性能数据与验证方法、异常边界、可维护性、线上问题和工程协作；5 年候选人按该层级上沿提问，不能只问概念定义或 API 用法。
- 6 年及以上：重点考查系统与架构设计、跨模块约束、规模化瓶颈、稳定性治理、长期演进、技术决策和团队工程效能；场景 / 设计题按 `references/architecture.md` §1 的四步流程组织题干和参考答案，并按 §2 要求候选人给出量化依据。

题目难度必须与经验层级匹配，但不得只因工作年限预设候选人已经掌握某项技术。对中高级候选人，题干应要求给出具体决策依据、测量方法、失败模式和取舍；对实习生或应届生，应允许使用课程、个人项目或假设场景说明思路。参考答案也必须匹配同一层级，不能用初级答案作为中高级题目的标准答案。

对 3 年及以上候选人，技术基础题不得以背诵定义、罗列 API、复述生命周期顺序或语言语法为主体；必须把基础原理放入真实故障、性能现象或系统约束中，要求候选人分析根因、验证路径和治理方案。例如不能只问 MonoBehaviour 生命周期函数的调用顺序，应改为异步场景加载、对象池反复激活或事件重复注册造成初始化状态错乱的排查与生命周期设计。若只是为了确认基础是否造假，可在“待确认”条目中列为快速排雷点，不占默认正式题目配额。

项目题点名具体项目并追问角色、方案、难点、数据和复盘；场景题结合候选人经历；软素质题引用具体经历。不得编造简历中未出现的数据、项目或候选人经历。

简历中每一处无量化的成果宣称（`(无量化)`、`显著降低`、`提效 200%` 等），至少要在“项目深挖”里出一道题向候选人索取：改造前后的具体数值、测量工具与条件、样本规模，以及本人写下哪部分代码。题干直接引用该宣称并要求给出基线与口径；参考答案写明“给不出前后数据与归属，则该成果视为未证实”。

6 年及以上或架构师岗位的技术决策、治理、跨团队与工程效能类软素质题，可从 `references/architecture.md` §7 列出的考点面中选取，但题干和答案仍必须落到候选人真实经历与岗位描述。

每道题使用以下格式：

```markdown
- [ ] **题目：** …

  **考点：** …

  **参考答案：** …
```

每道题、考点和参考答案必须放在同一个题目块内，并使用空行和加粗标签分隔；不得压缩到同一行。

每道题都必须给出简洁、可核验的参考答案要点，并完整回应题目中的每个子问题。

题干必须自带防漂移锚点，避免候选人把话题牵走（手法见 `references/interview-control.md` §2）：写清只讨论哪个模块或机制、显式编号多个子问题、性能与优化类题目明确要求基线值、目标值和测量条件、场景 / 设计题必须给出规模与延迟或可用性目标。参考答案逐一对应这些子问题。

技术题的答案必须覆盖“实现或运行流程 → 底层机制 → 影响结果 → 边界与取舍”的因果链，解释问题为何发生、消耗了什么资源、最终造成哪些可观察影响，不得只写“提升性能”“减少卡顿”等表层结论。例如涉及 GC 时，应说明短生命周期对象的频繁分配如何增加托管堆压力并触发垃圾回收，标记、重定位与压缩阶段如何消耗 CPU、引入暂停或帧时间抖动，并进一步影响吞吐、延迟和内存峰值；具体行为依赖运行时实现时，要明确区分通用原理与特定运行时结论。

参考题库已经为常见考点写好因果链骨架和弱答案信号，可作为答案深度的校准基准：`references/csharp-dotnet.md` §1 表格最后一列与 §2、§3，`references/unity-game.md` §2–§5，`references/architecture.md` §1–§3。校准深度不等于照抄要点：题目涉及候选人未使用过的运行时或管线时，只保留通用原理部分。

项目深挖、场景 / 设计和软素质题的答案说明优秀回答应覆盖的要点，不得代替候选人编造简历中未提供的经历、数据或结论。不要输出评分标准、追问清单、编程笔试或限时作业，除非用户明确要求。

### 数量与配额

默认按 3 分钟一题生成 10 题，对应 30 分钟。根据候选人的相关工作年限使用对应配额；工作年限无法确认时使用 1–2 年配额：

| --- | ---: | ---: | ---: | ---: | ---: |
| 实习生 / 应届生 | 4 | 2 | 2 | 1 | 1 |
| 1–2 年 | 3 | 3 | 2 | 1 | 1 |
| 3–5 年 | 1 | 3 | 3 | 2 | 1 |
| 6 年及以上 | 1 | 3 | 2 | 3 | 1 |

2.3 默认覆盖两个不同项目。用户指定总时长时，题目数为总分钟数除以单题分钟数并四舍五入；用户指定单题时长时使用该时长，否则仍按 3 分钟。

题目多于 10 道时，实习生 / 应届生和 1–2 年候选人按 2.1、2.2、2.3 的顺序循环增加，3 年及以上候选人按 2.2、2.3、2.4 的顺序循环增加。题目少于 10 道时，从对应层级中题数最多的分类依次减少；2.1、2.4 和 2.5 不得少于 1 道。配额用满即停。

### 可读性与长度要求

“简历总结”是给面试官三秒扫读的表，不是分析笔记。信息多就少写，不许挤成行。

- 一行或一格最多 3 项事实、40 字内；第 4 项必须拆到骨架已有的多行结构里（每段经历一行、每个维度一行、每条该面一行），不新开散文行续写。
- 骨架已给表格的地方必须用表格。禁止 `- **概况：** …` 式的项目符号长行，禁止把表格内容改写成加粗标签句，禁止在表格下方补说明段。
- 其他上限：证据依据 30 字、该面与不该面 35 字、待确认 25 字、控场话术 30 字、“能力”和“结论”各 70 字。超限先删修饰语和重复信息，仍超就删整条。
- 单元格内不换行、不用 `<br>`、不嵌套列表；一段经历一行，最多 1–2 个动作与结果，其余舍弃。
- 等级与结论只用固定取值（强 / 中 / 弱 / 无，建议面试 / 谨慎面试 / 不建议面试），不加括号解释；理由写进“依据”列或“不该面”。
- 判定过程（证据分级、年限门槛、配额计算、技术栈迁移）在内部完成，只输出结论和最直接的依据，不写推理过程，也不把骨架里的规则文字复述一遍。
- 同一事实只出现一次：待确认不得复述“不该面”，控场不得复述题目内容，“结论”不得再重复“该面”的理由。
- 不整段复制简历原句；引用时用不超过 15 字的短语加引号。
- 删除无归因的形容词（“基础扎实”“经验丰富”“精通”“全模块”）、与分组重复的技术罗列，以及岗位描述已写明信息的复述。
- “一、简历总结”整节不超过 45 行（含表格行，不含空行），条目数按骨架上限即止；面试题清单是文件主体，总结部分不得长于题目部分。
- 表格只使用骨架定义的列，不新增列、不改动列名。

反例（禁止，实际产出过的形态）：

```markdown
- **概况：** 张某｜某大学·某专业·大专（非 985/211；排名未收录）｜专业非直接相关｜自述近 5 年、时间线约 4 年 5 个月｜现离职｜方向 Unity3D，定位主程｜期望广州 U3D（11–20K）
```

正例：同一信息拆进“姓名 / 学历”“年限 / 状态”“方向 / 定位”“期望”四个单元格，每格一条，未收录榜单、非直接相关等修饰语删除。

输出前逐条自检，任一不过就重写该条后再输出：

1. 无 `- **标签：**` 形式的总结条目，无表格外的散文段。
2. 无一行或一格含 4 项以上事实；每个单元格在 40 字内。
3. “能力”行与“该面”无弱证据、无量化条目；每条量化说法都能指到简历里的机制与数据。
4. 同一事实未出现在两处；无 `<…>` 占位符、无骨架规则原文。
5. 总结整节 ≤45 行，且不长于题目部分。
