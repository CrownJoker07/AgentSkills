# 面试控场技巧（避免被候选人带着跑）

> 本文件为**本仓库整理**：基于 `csharp-dotnet.md`、`unity-game.md`、`architecture.md` 的考点结构与 SKILL.md 的固定分类、配额和题目格式整理出的面试官控场规范，不对应任何外部来源，不使用 `[Sxxx]` 编号。
>
> 用途：在“四、面试官备注”中输出控场提示，并在面试执行阶段防止话题被候选人牵走、导致预设考点没有考察、证据无法横向比较。

---

## 1. 先定义什么叫“被带着跑”

以下情形都算失控，不算正常发挥：

| 现象 | 判断标准 | 实质后果 |
| --- | --- | --- |
| 话题漂移 | 回答结束时的主题与题干考点不是同一件事，且未回答原题 | 预设考点未覆盖，横向比较失效 |
| 子问题失踪 | 题干有 2 个以上子问题，只答了最熟悉的那一个 | 只能给“部分回答”，不能按完整答案给分 |
| 时长失控 | 单题明显超过每题预设时长，挤占后面题目 | 后面的分类（尤其 3.4、3.5）被砍掉 |
| 名词替代机制 | 大量术语和组件名，没有流程、没有因果、没有数据 | 无法判定深度，容易把“知道名字”记成“会” |
| 反客为主 | 候选人开始反问、纠正题干、要求先聊架构背景、指定下一题方向 | 面试节奏与考点选择权转移 |
| 故事化 | 用长篇项目背景、团队故事、行业评论替代技术分析 | 得到的是经历叙述，不是能力证据 |
| 单方面换栈 | 被问 A 技术，改口讲熟悉的 B 技术并声称等价 | A 的考点没有证据，B 也不是原岗核心 |
| 结论无边界 | “这样肯定没问题”“我们线上都这么做” | 缺少边界与取舍，属于弱证据信号 |

**原则**：候选人可以选表达方式，不能选考点。考点由简历证据和岗位描述决定（见 SKILL.md 的选题规则），不能由候选人熟悉什么决定。

---

## 2. 出题阶段的四个防漂移锚点（写进题干）

题干写得好，失控概率显著下降。生成每道题时确保：

1. **限定范围与层次**：写清“只谈 `<模块 / 机制>`，不要展开项目背景”，并指明要答的层次（现象 / 根因 / 验证 / 取舍）。
2. **拆成显式子问题**：多问句题干用“先…再…最后…”编号，让漏答变得可见。
3. **锁定数据要求**：性能与优化类题目在题干里写明要给出**基线值、目标值、测量条件**，否则容易漂到“我们优化了、变流畅了”这类表层结论。
4. **给出边界条件**：场景 / 设计题必须带规模、延迟或可用性目标、团队与成本约束；没有约束的开放题几乎必然被带跑（见 `architecture.md` §1、§2）。

---

## 3. 执行阶段的回收手法

- **口头锚定**：出题后一句收束，“这题我要听的是 `<机制链条>` 和 `<数据>`，`<不需要的部分>` 可以先略过”。
- **计时**：到时长 80% 时提示“请开始收口”，到点即进入下一题。时间配额来自 SKILL.md 的每题时长与分类配额，不因单题精彩而临时扩容。
- **复述式收口**：候选人跑远时，用“我把你的回答归成三点：…；原题问的是 X，这部分还没听到”把话题拉回，既给对方台阶，也留下明确记录。
- **点名缺失子问题**：直接问“第二问还没答：怎么验证？”——比再开一个新话题高效。
- **打断话术**：允许打断，但必须给回归属权。“这里先停一下，回头请你继续讲 `<他的话题>`；先把 `<原题点>` 说完。”
- **术语墙**：候选人堆名词时，随机挑两个要求解释关系、开销和失效条件（按 `csharp-dotnet.md` §1 最后一列、`unity-game.md` §5 的因果链要求）。
- **证据墙**：凡出现“优化了 / 稳定了 / 解决了”，统一追问四件事实：改之前后数字、测试条件、他本人做的具体决定、如何排除其他原因。
- **拒绝反向面试**：候选人反问时，明确“这个问题我在 `<面试官备注 / 后续环节>` 回答，现在先完成这一题”。
- **换栈回收**：候选人改口讲 B 技术时，先确认迁移有效性（`unity-game.md` §9），再收回原题：“B 的部分记为可迁移能力，A 的考点还需要一个明确回答。”

## 4. 各分类的专属防失控要点

| 分类 | 最易漂移方向 | 回收动作 |
| --- | --- | --- |
| 3.1 技术基础 | 变成背诵定义、或转成项目吐槽 | 要求落到一个具体故障或现象，说明机制链条 |
| 3.2 技术进阶 | 术语堆叠、把版本实现说成通用保证 | 追问“在哪个运行时 / 版本 / 配置下成立，如何测量” |
| 3.3 项目深挖 | 公司故事、团队流程、“我们”如何如何 | 每段背景限 30 秒，反复问“你个人做的决定是什么、数据变化是什么” |
| 3.4 场景 / 设计 | 组件名清单、直接跳实现、无估算 | 强制走四步：约束 → 高层设计 → 核心组件 → 扩展；每步要一句量化依据 |
| 3.5 软素质 | 泛化价值观、成功学、无归因结果 | 要求 STAR 式单一事件，并锁定候选人当时的选择与代价 |

## 5. 提问顺序与时间结构

- **先易后难不可取**：按配额表顺序推进（3.1 → 3.5），保证高价值分类不被前面的长答挤掉。
- **前 1/3 校准深度**：用前两道技术题快速定位候选人实际层级，之后按层级收紧或放宽追问，而不是继续按原题干照本宣科。
- **保留硬预算**：给 3.4、3.5 各预留至少一题的完整时间；若已被超时挤占，宁可砍掉 3.1、3.2 的备选题（配额减少规则见 SKILL.md）。
- **中断处理**：候选人主动要求“换个话题聊”时，只有在他明确承诺稍后回答原题时才允许，且必须记进“待回收”清单。

---

## 6. 记录规范（防被带跑之后的评分污染）

- 只记**证据**：机制链条讲到哪一层、给了什么数字、验证方法是否成立、边界是否说清。
- 不记**话题广度**：候选人谈了五个技术不等于会五个；每题记一条“原题答了/漏答了”，漏答的子问题写进“信息不足的项目”。
- 话题被牵走的题标注 `漂移`，并在“需要确认的方向”里写明该考点实际未被覆盖、横向比较时不能与其他候选人的同一考点直接对比。
- 复盘区分两件事：候选人回答质量差 vs 自己没控住导致没考察到。后者不能写成候选人的能力结论。

---

## 7. 输出映射

写入本技能输出骨架时：

- 技术基础 / 技术进阶题：把本题最可能的漂移方向（背景化、名词化）和一句话回收提示写入“控场提示”，不写进题干也不新增题目。
- 项目深挖题：控场提示聚焦“30 秒背景限制 + 个人决定 + 前后数据”。
- 场景 / 设计题：控场提示给出必须收口的四步和至少一个量化点。
- 只输出 1–2 条**本题最可能失效**的提示，不做通用技巧清单（通用清单见本文件）。
- 控场提示属于面试官备注，不得转写进题目、考点或参考答案。

---

## 8. 不得做的事

- 不得为了“聊得开”而临时换成候选人主导的开放话题，导致预设分类未覆盖。
- 不得用打断代替追问；打断后必须给出明确的回收题目和剩余时间。
- 不得因为候选人讲得生动就补写简历中没有的数据、项目或结论（受 SKILL.md“不得编造”约束）。
- 不得把候选人的技术栈偏好当成岗位选型依据，或据此改写岗位核心考点。
- 不得输出评分标准、追问清单、编程笔试或限时作业；本文件只提供控场提示，仍遵守 SKILL.md 的输出范围。
