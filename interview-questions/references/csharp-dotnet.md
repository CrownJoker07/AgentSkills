# C# / .NET 考点地图（技术基础与技术进阶）

## 0. 用途

用于主力语言为 C# 的候选人生成 **3.1 技术基础**、**3.2 技术进阶** 和主力语言深度题。

- 本文件给的是**考点范围和参考答案的深度基准**，不是题库原文。题目必须结合候选人简历里的真实场景重写。
- 表中标注的层级对应 SKILL.md 的年限分层：`L1` 实习 / 应届、`L2` 1–2 年、`L3` 3–5 年、`L4` 6 年及以上。
- 涉及运行时行为时，答案必须区分：**C# 语言规范** / **.NET（CoreCLR）与 Unity 的 Mono 运行时实现** / **特定版本或配置行为**。
- 只挑与候选人经历和岗位相关的一条问题链深挖，不要把互不相关的底层知识堆进同一道题。

## 1. 考点分层地图

| 考点 | L1 问法 | L3 / L4 问法 | 参考答案必须覆盖的因果链 |
| --- | --- | --- | --- |
| 托管堆与分配 | 值类型与引用类型分别存在哪里 | 高频小对象分配如何影响工作集与帧时间 | 指针递增分配 → 分配速率决定回收频率 → 存活集大小决定暂停时长 → 吞吐、延迟抖动、峰值内存 |
| GC 代与 LOH | Gen0/1/2 是什么 | 为什么 Gen2 回收比 Gen0 贵、LOH 为什么会碎片 | 新对象入 Gen0 → 存活即晋升 → 高层回收需遍历更大对象集与更多引用 → LOH 默认不压缩 → 大数组反复创建造成地址空洞与峰值内存 [S001] |
| GC 触发与自适应 | 什么时候会 GC | 长期运行内存缓慢增长如何定位 | 低物理内存 / 分配超阈值 / 显式 `GC.Collect` 三种条件；生存率高则提高分配阈值；工作集与回收频率之间自适应平衡 [S001] |
| Workstation / Server GC | — | 服务端与客户端为什么用不同模式 | Server GC 每逻辑 CPU 一个回收堆与并行回收 → 吞吐高但内存占用更大；客户端进程用 Workstation 更省内存 [S001] |
| roots 与可达性 | 什么是引用链 | 事件订阅 / 静态集合 / 非托管 handle 为何造成泄漏 | 栈 root、静态字段、GC handle、finalizer 队列构成根集；被根集可达即存活 → 生命周期被动延长 → 对象及其引用的整棵子树无法释放 |
| `Dispose` / finalizer | `using` 的作用 | 为什么不要依赖析构释放非托管资源 | 非托管资源 GC 不知情 → 必须显式 `Dispose`；finalizer 使对象至少多活一轮 GC、在终结线程执行、顺序与时机不可控 → 用 `SafeHandle` 包装 [S001] |
| 装箱与泛型 | 什么是装箱 | 集合、闭包、接口调用中的隐性装箱在哪 | 装箱 = 堆上分配对象头 + 拷贝值 + 返回引用 → 抬高分配速率与 Gen0 回收频率；`List<int>` 等泛型容器避免装箱；非泛型集合、值类型转 `object`、把值类型当接口或 `object` 调用 `Equals` / `GetHashCode` / `ToString` 时仍可能装箱（具体取决于是否命中特化实现） |
| `class` vs `struct` | 两者区别 | 大 struct、可变 struct、防御性拷贝造成的隐性开销 | struct 无对象头、可栈上或内联进容器，但赋值是整体拷贝、装箱会拷贝两份、属性返回内部 struct 的可变成员引发防御性拷贝；`in` 参数与 `readonly struct` 用于削减拷贝 [S004] |
| `Span<T>` / `stackalloc` / `ref struct` | — | 零拷贝解析热路径数据如何设计 | `ref struct` 禁止作为字段、装箱和跨 `await` 存活 → 保证生命周期不超出其来源内存，也因此无法进入 LINQ 闭包；`stackalloc` 随方法返回释放，默认清零（`unsafe` 且不显式初始化时可省略清零），需控制单次大小与越界访问 |
| `ref` / `out` / `in` / ref return | `ref` 与 `out` 区别 | 引用返回带来的悬垂与逃逸风险 | `ref` 需先初始化、`out` 必须在被调方法内赋值；引用参数不拷贝，但会阻止部分优化并要求地址稳定；数组元素按 `ref` 传递需处理边界与 GC 移动 [S004] |
| `const` vs `readonly` | 区别是什么 | 跨程序集引用常量为什么会有版本问题 | `const` 编译期内联进调用方 IL → 重新编译依赖方才生效；`readonly` 运行时在构造期赋值，可用于引用类型 [S004] |
| 虚方法 / 接口调度 | `virtual` / `override` 作用 | 多态调用在热路径上的开销与可去虚化 | 虚调用查 vtable、接口调用需类型查找（缓存加速）→ 相比直调更多指令；`sealed` / 具体类型 / 泛型参数约束有利于去虚化与内联；属实现层面优化，不得表述为语言保证 |
| 抽象类 vs 接口 | 区别 | 契约演进时如何选择（默认接口实现、版本兼容） | 抽象类可带状态与构造、单继承；接口只声明契约、可多实现、支持默认实现但无法承载实例状态 [S004] |
| 重写 vs 隐藏 | `override` 与 `new` 区别 | 通过基类引用调用时的实际分派结果 | 隐藏按编译期静态类型选择成员，重写按运行时类型分派 → 集合中存基类引用时行为不同，属易错点，适合作排雷题 |
| `==` 与 `Equals` | 区别 | 自定义类型的相等与哈希契约 | 引用类型默认 `==` 与 `Equals` 均为引用相等；`string` 重载为值比较；自定义值语义须同时重写 `Equals` / `GetHashCode`，相等的对象哈希码必须相同，否则字典行为错误 [S004] |
| 泛型与协变逆变 | 泛型解决什么问题 | 运行时类型实例化、值类型独立代码、引用类型共享 | 泛型免除装箱与强制转换、提供类型安全；引用类型共享本地化代码、值类型各自生成代码；`IEnumerable<out T>` / `Action<in T>` 只在类型参数完全处于输出或输入位置时合法 [S004] |
| 集合内部实现 | `List<T>` 与 `T[]` 区别 | 遍历中修改集合、字典 key 变更后行为 | `List<T>` 容量增长触发数组重分配与拷贝；`Dictionary<K,V>` 不保证枚举顺序、`Add`/`Remove` 期间枚举会抛异常；值类型 key 的重写 `GetHashCode` 会破坏查找 [S004] |
| `IEnumerable` / `ICollection` / `IList` | 三者关系 | 参数与返回值类型如何选择 | 能力递增：只读迭代 / 计数与增删 / 索引访问；参数用最小够用的接口以降低耦合 [S004] |
| 委托与事件 | 委托是什么 | 事件订阅造成的对象生命周期与内存问题 | 委托是持有目标与方法的对象，组合时生成新实例 →  +=/-= 有分配；`event` 限制外部只能加减；发布者生命周期长于订阅者且未取消订阅 → 订阅者与整棵对象图存活 |
| LINQ 与延迟执行 | 查询语法与方法语法 | 一次查询里的多次枚举、分配与调试难度 | `IEnumerable<T>` 扩展方法返回迭代器 → 每次枚举重新执行；枚举中修改源集合导致结果异常；`ToList()` 决定执行时机与内存驻留；对 `IQueryable<T>` 才翻译为远端查询 [S004] |
| 闭包 | — | 循环变量捕获导致的错误行为与分配 | 被捕获变量提升为显示类实例 → 每次捕获分配、生命周期随委托；多个委托共享同一变量导致逻辑错误；重构为局部副本或方法参数 |
| `async` / `await` | 解决什么问题 | 状态机、上下文捕获、死锁与线程池饥饿 | `await` 挂起方法为状态机并把延续注册到当前 `SynchronizationContext` / TaskScheduler；无上下文的纯异步不会固定回原线程；`Task.Result` / `Wait()` 阻塞拥有上下文的线程 → 延续排队等不到线程 = 死锁；`async void` 异常无法被捕获，仅限事件处理器；CPU 密集工作放 `async` 方法里仍是同步阻塞 [S003] |
| `Task` vs `Thread` | 区别 | 为何不能靠新建线程处理并发规模 | 线程是 OS 级资源、栈与调度开销大；`Task` 是任务抽象，多数在 ThreadPool 上执行、可组合与取消；阻塞式等待会占用池线程 → 饥饿与延迟放大 [S004] |
| `ValueTask` / 池化 | — | 高频异步接口的分配与误用 | `ValueTask` 可承载同步完成的零分配路径，但只能 `await` 一次、不可并发使用；滥用反而引入风险 |
| 取消与超时 | `CancellationToken` 用法 | 未传播 token 造成的资源泄漏 | token 协作式取消；未 `Register` 的回调、未传 token 的下层 I/O 在取消后仍在执行 → 请求堆积 |
| lock 与内存模型 | `lock` 语法 | 可见性与重排问题、`volatile` 的边界 | `lock`（Monitor）保证互斥并提供内存屏障语义；`volatile` 只保证可见性/顺序性的一部分场景，不保证复合操作原子性；计数应使用 `Interlocked` 或锁 [S001] |
| 死锁与竞态 | 常见并发 bug | 用锁顺序 / 超时 / 无锁结构给出方案与验证方法 | 循环等待、持锁调用外部异步或反向调用造成死锁；验证依赖压力测试、可观测计数、可复现的最小用例 |
| 反射 | 反射做什么 | 热路径反射的成本与替代 | 反射需在运行时构造元数据视图、参数装箱、无法内联 → 比直调慢且难以 AOT；替代：编译期代码生成（Source Generator）、表达式树编译成委托、缓存 `MethodInfo`、接口直调 [S004] |
| 提前 / 延迟绑定 | 区别 | AOT 后端下的限制 | 编译期确定目标 vs 运行时按名字查找；AOT / IL2CPP 下运行时 emit、动态程序集加载与未保留类型的反射会失效，需 link xml / 保留特性 [S004][S019] |
| 序列化 | — | 大对象图序列化的分配与版本兼容 | 反射式序列化的临时集合与字符串分配；契约演进（未知字段、可选字段、schema 版本）；二进制 vs 文本格式在体积、CPU、跨端一致性上的取舍 |
| ASP.NET Core 管道 | 中间件是什么 | 注册顺序造成的鉴权与异常处理问题 | 请求正向穿过中间件、响应逆向返回；`UseRouting` / `UseAuthentication` / `UseAuthorization` 顺序错误会导致策略判定用错身份；自定义中间件用 `RequestDelegate`；顺序是行为契约的一部分 [S004] |
| 依赖注入 | 三种生命周期 | Captive Dependency 与作用域泄漏 | Singleton 持有 Scoped 会使其实际变成单例（并发共享、状态跨请求）；`ServiceProvider` 建立子作用域需释放；构造注入优于服务定位 |
| EF Core | ORM 解决什么 | 性能陷阱与一致性 | 变更跟踪带来额外内存与快照开销，只读查询用 `AsNoTracking`；懒加载触发 N+1；不可翻译的表达式回退到客户端求值会拉全表；并发用行版本 / 乐观并发；迁移与线上变更流程 [S004] |

## 2. GC 与内存深度题（首选问题链）

**题干模板**（L3 / L4）：

> 线上服务 / 客户端长时间运行后内存曲线持续上升，且伴随周期性帧时间尖峰（或 P99 延迟尖峰）。请描述你的定位路径、判定依据、可能的根因清单，以及你最终方案与验证方式。

**参考答案要点（按因果链）**：

1. **先分层归因**：区分托管堆增长、非托管/native 内存增长、内存映射与文件缓存增长；用指标（GC 各代大小、GC 次数与耗时、堆上对象类型直方图、句柄数、RSS）而不是只看任务管理器数字。[S001][S002]
2. **机制**：分配速率决定 Gen0 回收频率；若对象被根集持续可达则存活并晋升到 Gen2；Gen2 / LOH 回收需要遍历更大对象集，默认不压缩 LOH，导致分配指针推进与地址空洞并存 → 表现为“内存不降 + 偶发长暂停 + 峰值继续抬高”。
3. **根因清单**：事件订阅未取消、静态集合 / 缓存无上限、`IDisposable` 未释放（含 `CancellationTokenRegistration`）、非托管 buffer 未归还、循环引用 + finalizer 使对象多活一轮、异常与日志累积、临时大数组进 LOH、字符串拼接、装箱热点。
4. **可观测的验证**：两次快照 diff 定位新增类型与引用链；修改后用同一负载、同一时长对比分配速率、GC 次数、Gen2 次数、工作集与尖峰分位数；说明为什么这个证据能归因到自己的改动。
5. **取舍**：降分配 vs 代码复杂度；对象池复用带来的状态污染与驻留内存上升；调 GC 模式 / 堆上限换来吞吐但抬高常驻内存；`GC.Collect` 只能作为验证手段或特定时机使用，不作为常规优化。

**弱答案信号**：只会说“`GC.Collect()` 强制回收”“加对象池就流畅了”；说不出根集 / 代 / LOH 与暂停的关系；用平均帧时间代替分布；没有前后基线与同负载复现。

## 3. `async` 与线程深度题（备选问题链）

**题干模板**：

> 一段 `async` 调用链在高并发下出现整体响应时间雪崩，甚至偶发完全不返回。给出你的排查步骤、两种以上可能的机制解释、以及修复方案与验证方式。

**参考答案要点**：

- 机制一：`.Result` / `Wait()` 在持有同步上下文的线程上阻塞，延续排队到同一个被阻塞的上下文 → 自锁死；库代码用 `ConfigureAwait(false)`，应用层不要阻塞等待，或把阻塞点搬到独立线程。
- 机制二：池线程被阻塞 I/O 或 CPU 密集代码占满 → 后续任务排队、延迟非线性放大；区分 I/O 密集（不该占线程）与 CPU 密集（应限并发、可 `TaskScheduler` 隔离）。
- 机制三：锁 / 信号量的等待顺序或超时缺失；`Task.WhenAll` 的异常聚合与取消传播不完整导致半提交状态。
- 定位：线程数、队列长度、池线程 busy 计数、dump 中各线程栈、超时与重试统计。
- 修复：端到端传播取消与超时、限制并发度而非无限开任务、把远程调用改为并行等待而非串行、幂等与重试退避。

**边界**：`await` 之后是否回到原线程取决于运行时与 `SynchronizationContext`；WinForms / WPF / ASP.NET（旧）/ Unity 各不相同，不得把某一环境行为说成 C# 规则。

## 4. 技术基础题的出题约束

- 3 年及以上：不使用“什么是 X / X 和 Y 的区别”这类背诵题作为正式题目；把同一知识点放进故障、性能或约束场景中（例：`Dictionary<K,V>` 放进“同一实例被并发读写导致 CPU 打满或数据丢失”的排查题）。
- 实习 / 应届：允许概念与流程题，但要求给出简单代码或流程说明，并能说出一个常见错误。
- 允许作为快速排雷点（写进面试官备注，不占正式题配额）：生命周期顺序、访问修饰符枚举、`const` / `readonly` 差异、`IEnumerable` 与 `IList` 关系。

## 5. 不得作为考点的内容

- 冷门语法输出的记忆题、生僻标准库 API 名称、C# 版本特性清单背诵。

- 把 Unity 的 Mono 运行时行为当成 .NET（CoreCLR）结论，或反之；跨运行时对比时明确写清是哪一边。
