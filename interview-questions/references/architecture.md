# 架构师 / 系统设计 考点地图

## 0. 用途

用于 **6 年及以上候选人、架构师 / 技术负责人岗位**，主要覆盖 **3.4 场景 / 设计**，也用于 3.2 中需要系统视角的题目和 3.5 的决策类软素质题。

- 每题必须落到具体约束（规模、延迟目标、可用性目标、团队与成本限制），并给出量化依据；只罗列组件与名词不构成答案。
- 候选人简历没有生产系统证据时，不出“设计一个百万在线平台”这类题；改用 §7 的演进与治理题，让其基于真实小系统说明决策过程。
- 参考答案说明“优秀回答应覆盖的要点与取舍”，不编造候选人未提供的数据和经历。

---

## 1. 答题流程框架（用于判断候选人是否主导讨论）

**来源：[S043] 的四步法 + [S040] 的职责划分，本仓库整理为面试评价口径。**

1. **澄清场景与约束**：谁用、怎么用、读写比、峰值与均值、数据规模、延迟与可用性目标、一致性要求、成本与团队约束、合规与故障容忍。
2. **高层设计**：主要组件、数据流、同步与异步边界、状态存储位置；说明为什么这样切分。
3. **核心组件细化**：接口、数据模型、索引与访问模式、并发与失败语义、瓶颈点。
4. **扩展与治理**：容量估算、水平扩展、缓存与分片、故障切换、可观测性、发布与回滚、演进路径与被放弃的方案。

**评价口径**：初级候选人在第 2 步就跳进实现；成熟候选人主动收敛约束并说明假设；架构师级候选人会明确指出取舍代价、失败模式、迁移与回滚路径，并能用数据支持判断。

## 2. 量化速查（答案必须能自己推，不接受背表）

- **单位与倍数**：1 KB ≈ 千字节，1 MB ≈ 百万，1 GB ≈ 十亿，1 TB ≈ 万亿；2 的幂对照表（`2^10 = 1 KiB`，`2^30 ≈ 1 GiB`）。[S043]
- **量级直觉（数量级，不是精确值）**：L1 缓存纳秒级、内存约百纳秒级、同机房 RTT 约几十到几百微秒、SSD 随机读十到百微秒、机械盘毫秒级、跨地域 RTT 数十到数百毫秒。用于判断“一次远程调用相当于几十次内存访问”这类推理。
- **可用性数字**：99.9% ≈ 年 8.8 小时不可用；99.99% ≈ 年 53 分钟。停机预算决定冗余、发布与故障恢复设计。
- **三步估算法**：写请求量 = QPS × 写大小 × 副本数 → 存储 = 日增 × 保留期 ×（1 + 索引/压缩系数）→ 带宽 = QPS × 响应大小 ×（1 + 缓存未命中率）。
- **线程与连接预算**：并发 = QPS × 平均延迟（Little 定律）；据此判断需要的实例数、连接池大小和队列上限，并推导过载时的表现。

**红旗**：不做估算就选组件；用“加机器 / 上 Redis / 换微服务”当万能结论；说不出容量模型对瓶颈的影响。

## 3. 通用机制考点表

| 考点 | 优秀回答要点 | 高频错误 | 来源 |
| --- | --- | --- | --- |
| 性能 vs 可扩展性 | 性能是单用户变快，可扩展是负载增长时仍能按比例服务；先定位是哪一类问题 | 把两者混为一谈 | [S043] |
| 延迟 vs 吞吐 | 明确目标（可接受延迟下最大化吞吐），说明批处理、并发与队列深度如何改变这一权衡 | 只报平均延迟 | [S043] |
| CAP 与一致性模式 | 网络必然分区，故必须在 C 与 A 之间选；弱一致 / 最终一致 / 强一致的适用业务 | 说“三者可任选其二所以分区时放弃网络” | [S043] |
| 负载均衡 L4 / L7 | L4 按地址端口与 NAT 转发，开销小；L7 可读请求头 / cookie 做路由、SSL 终结、会话保持 | 分不清两者能力边界 | [S043] |
| 反向代理 | 收敛入口、隐藏后端、SSL 终结、压缩、缓存、静态内容 | 与负载均衡器混为一谈 | [S043] |
| CDN 推送 / 拉取 | push 写多读少、pull 高流量静态；TTL 与内容失效、URL 改写 | 忽略缓存不一致窗口与成本 | [S043] |
| 缓存层次与更新策略 | 客户端 / CDN / Web / 应用 / 数据库查询级 / 对象级；cache-aside、write-through、write-back、refresh-ahead 的一致性、丢失风险与实现复杂度 | 只答“加 Redis”；说不出失效策略与热点 key | [S043] |
| 复制与故障切换 | 主从（读写分离、提升逻辑、复制延迟）、主主（写冲突与一致性代价）、active-passive 与 active-active、宕机时间与热备 | 忽略复制滞后对读己写一致的影响 | [S043] |
| 分片与一致性哈希 | 按 key / 范围 / 哈希分片，再平衡代价、热点倾斜、跨片查询与事务的限制 | 忽略跨片聚合与运维复杂度 | [S043] |
| 联合（按功能分库） | 减少单库压力与复制滞后、可并行写；跨库 join 与应用路由复杂化 | 当成完全替代品使用 | [S043] |
| 非规范化 | 以写换读、避免高成本 join；冗余同步约束与写放大 | 忽视数据不一致风险 | [S043] |
| RDBMS 扩展 | ACID、索引（B 树、写放大与内存占用）、慢查询、覆盖索引、批量写入、连接池 | 只说“加索引” | [S043] |
| NoSQL 选型 | 键值 / 文档 / 宽列 / 图四类的数据模型、访问模式、事务与一致性边界；BASE 与最终一致 | 按流行度而非访问模式选 | [S043] |
| 消息与任务队列 | 解耦与削峰、竞争消费者与水平扩展、至少一次语义下的幂等、顺序保证的代价、死信与重试、背压 | 认为消息投递“恰好一次”免费 | [S043][S042] |
| 可靠性模式 | 重试 + 指数退避 + 抖动、幂等键、超时、断路器、舱壁隔离、优雅降级、限流、优先级队列 | 无超时的重试风暴 | [S042] |
| 分布式一致性 | 2PC 的资源占用与协调者单点、Saga 补偿与可见状态、Outbox 与变更数据捕获保证发消息与写库的原子性、事件溯源 + CQRS 的投影重建与最终一致 | 把“最终一致”当成不一致也没关系 | [S042][S040] |
| 服务发现与配置 | 注册与健康检查、租约与过期、配置版本与灰度下发、下线的连接排空 | 只答“用 K8s” | [S043] |
| 可观测性 | 指标（聚合）/ 日志（明细）/ 分布式追踪（跨服务因果与关键路径）分工；SLO 与告警分层；采样与成本 | 三者互换使用 | [S040] |
| 安全与权限 | 认证与授权分离、令牌生命周期与吊销、最小权限与密钥轮换、多租户数据边界（库级 / schema / 行级）、注入与越权常见面 | 只做边界防护、内部服务全信任 | [S040][S041] |
| 数据迁移与发布 | 双写 / 影子读、增量对账、灰度与开关、回滚窗口、schema 演进兼容（加列可空、迁移分批） | 一次性大切换无回滚 | [S040][S042] |
| 成本优化 | 单位请求成本、冷热分层、实例与存储类型选择、预留与弹性组合、成本可观测 | 只看性能不看单位成本 | [S041] |

## 4. 经典设计题清单（结合候选人经历改写，不直接照抄）

来源：[S043] 的面试题集与本仓库整理。每题给出“主要考点”，用于决定放在 3.4 还是 3.2。

| 设计题 | 主要考点 |
| --- | --- |
| URL 短链 / Pastebin | 发号与哈希冲突、Base62、读写比、缓存与 TTL、热点、分片键选择 |
| 社交 Feed / 时间线 | 推模式与拉模式、扇出成本、混合策略、分页与游标、一致性窗口 |
| 分布式 Key-Value 存储 / 查询缓存 | 分片与副本、一致性哈希、版本与失效、故障检测与再平衡 |
| IM / 消息系统 | 在线状态、消息顺序与去重、离线拉取、扇出与限流、多端同步 |
| 排行榜 / 计数服务 | 有序结构、增量更新的原子性、热点计数、近似与精确的取舍 |
| 通知 / 配置中心 | 长连接与轮询、增量下发、版本与回滚、鉴权与灰度 |
| 网页爬虫 | 抓取调度、去重（Bloom）、礼貌性与限速、DNS 与代理池、URL  Frontier |
| 对象存储 / 上传服务 | 分片上传与断点续传、元数据与配额、去重、CDN 回源、冷热分层 |
| 秒杀 / 高并发票务 | 库存扣减原子性、削峰与限流、下单与支付解耦、防重与对账 |
| 百万用户级系统 | 分层容量估算、状态外置、自动扩缩、多可用区与故障演练 |
| 单体拆分（真实系统） | 边界依据（数据所有权与变更频率）、Strangler Fig、双写与对账、独立部署的前置条件 |

**游戏 / 客户端架构方向可替换为**：战斗服与网关分层、房间与场景的分片、帧同步服务器与回放、跨服与合服的数据迁移、客户端热更与资源管线、ECS 化改造的收益与成本（见 `unity-game.md` §7）。

## 5. 代码与对象设计题（适合 3–5 年，可进 3.2 或 3.4）

来源：[S043] OO 设计题清单。要求给出接口、数据结构与并发边界，而不是只画类图。

- LRU 缓存：容量与淘汰、`O(1)` 读写、线程安全与分片锁、持久化与过期策略。
- HashMap：哈希与冲突、扩容与重分布、相等与哈希契约、并发版本的行为差异。
- 停车场 / 牌局 / 呼叫中心：实体与状态建模、扩展点、规则可配置性、测试切面。
- 有限状态机 / 行为树求值器：状态迁移与副作用、可调试性、时间与确定性（对应游戏方向）。

## 6. 架构风格与技术选型取舍

**已核实的官方口径** [S040]：云上的典型设计是功能与数据分解分布、面向弹性伸缩、多语言持久化、异步处理、为故障做准备并度量修复时间、按需以基础设施即代码供给、不可变可替换的基础设施。同时明确指出：**并不是非用微服务不可**，云托管只是让许多设计模式更容易落地。

**微服务取舍** [S044][S042]：

- 收益：强模块边界（边界靠进程隔离变硬，跨模块绕行更难）、独立部署（改动只需测试与发布小服务，故障可降级）、技术多样性与库版本隔离、可按服务做安全隔离。
- 代价：分布式（远程调用慢且随时可能失败，需要更粗的调用粒度与异步化，异步又更难调试）、最终一致性（去中心化数据管理使跨服务更新无法用单事务，必须处理不一致窗口与对账）、运营复杂度（服务数量与频繁发布要求成熟的持续交付、监控与 DevOps 文化；复杂度并未消失，只是转移到服务之间的连接上）。
- 结论口径：存在“微服务溢价”，简单系统用单体更划算；边界划错会让收益变代价；“Monolith First”是合理策略；单体同样可以有良好的模块化与持续交付，只是依赖纪律。次要因素：单服务扩缩、安全隔离、测试难度。

**评价口径（架构师级信号）**：能说明当前团队规模与交付能力对风格的约束；能指出数据所有权与服务边界的判据；能给出可验证的拆分与回滚步骤；能承认并量化运维与一致性代价；能说明在什么条件下会重新选择相反的方案。

**反模式**：为了简历好看而拆；用架构名词替代问题分析；只讲收益不讲代价；把“上 K8s / 上中台 / 换语言”当决策；把团队沟通问题伪装成技术问题（康威定律方向相反时未察觉）。

## 7. 治理、演进与软素质考点

来源：本仓库整理（架构师岗位常见职责面），可放在 3.4 与 3.5。

- **技术债管理**：如何量化债（缺陷率、交付前置时间、回归成本）、偿还是否排进迭代、什么债明确不还。
- **长期演进**：接口与 schema 的兼容策略、废弃流程、跨版本数据迁移、多版本共存与客户端不可控升级。
- **质量属性与权衡**：性能、可用性、可维护性、可观测性、安全、成本之间的显式取舍；用一个真实决策说明放弃了什么。
- **决策与影响**：如何在信息不完整时决策、如何记录决策（ADR 类做法）、如何说服反对意见、事后被证明错了怎么办。
- **跨团队与组织**：服务边界与团队边界不一致时如何处理、公共组件的归属与维护、规范落地靠工具还是靠评审。
- **线上稳定性**：故障定位与止血优先级、复盘的根因深度与行动项闭环、演练与预案、SLO 与告警疲劳。
- **工程效能**：CI/CD、测试金字塔与自动化覆盖的真实收益、代码评审标准、发布频率与失败率的关系、度量指标如何防止被优化成数字游戏。
- **带人与评审**：技术判断分歧的处理、辅导他人做出的方案出了问题如何归因、如何评估他人代码质量而不越界。

**每题答案要点统一要求**：具体情境 → 候选人的角色与决策 → 依据的数据或约束 → 结果 → 复盘后的改动。缺失任一环节视为证据不足。

## 8. 不得作为考点的内容

- 框架与中间件源码细节背诵、版本配置项名称填空。
- 无约束条件的开放题（“设计一个系统”而不给规模、延迟、预算、团队条件）。
- 用某个特定云产品的名词作为唯一正确答案。
- 只问“什么是 DDD / 中台 / 云原生”，而不要求给出边界判据、代价与失败场景。
