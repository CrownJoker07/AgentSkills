# 游戏设计分析原则（Game Design Principles）

## 0. 用途

用于分析：

- 游戏机制
- 核心循环
- 玩家决策
- 信息与反馈
- 系统之间的相互作用
- 机制如何可能形成玩家行为和体验

本文件不是“怎样做一个好游戏”的万能公式，而是一套拆解与推理工具。

---

## 1. 先描述系统，再评价系统

**来源：[S002]**
**整理方式：在 Formal Elements 与 Critical Analysis 基础上二次整理。**

在说“好玩/不好玩”“合理/不合理”前，先描述客观结构。

至少识别：

### 玩家与参与者

- 谁在行动？
- 单人、合作、竞争、异步还是混合？
- 玩家角色是否对称？
- 是否存在 AI、环境、其他玩家等行为主体？

### 目标（Objectives）

- 当前动作的直接目标是什么？
- 本局/本次 Session 的目标是什么？
- 长期目标是什么？
- 是系统明确告诉玩家，还是玩家自己形成？

### 规则（Rules）

把规则拆成：

- 进入条件
- 可执行行为
- 自动触发行为
- 状态变化
- 成功/失败
- 重置/退出

### 资源（Resources）

资源不限于货币。

可能包括：

- 金币
- 钻石
- 体力
- 尝试次数
- HP
- 时间
- 道具
- 背包空间
- 信息
- 地图控制权
- 社交关系

### 状态（Game State）

说明玩家行为会改变什么状态：

```text
旧状态 + 行为 + 规则 → 新状态
```

### 信息（Information）

对每个关键决策检查：

- 玩家在行动前知道什么？
- 什么是隐藏信息？
- 什么是随机性？
- 什么只是 UI 没说清楚？

**Agent 规则：**

> 不要把“规则存在”与“玩家理解规则”视为同一件事。

## 2. 玩家意图与可感知结果

**来源：[S002]**
**原始概念：Player Intention / Perceivable Consequence。**

一个有意义的互动，通常至少需要：

### 玩家能形成意图

玩家需要能够：

- 形成目标
- 做出计划
- 在多个可能行为之间选择

不要求玩家知道所有结果，但至少应有足够信息形成合理判断。

### 系统反馈结果

玩家行动后，要能知道：

- 发生了什么
- 为什么发生
- 哪个状态发生变化
- 是否接近目标

如果玩家按下按钮后后台状态改变了，但玩家无法理解变化，则“实现正确”不等于“体验正确”。

**结论边界：**

代码只能证明系统有反馈逻辑，不能证明玩家真正理解反馈。

需要 Observation / Playtest 等玩家证据验证。[S011]

## 3. 使用 MDA 分层，不要跨层跳结论

**来源：[S009]**
**整理方式：将 MDA 转化为项目分析链。**

### Mechanics — 机制

项目明确实现的规则。

例如：

- 冷却 30 分钟
- 失败扣 1 次挑战机会
- Top 10 获得奖励
- 每赛季重置排行榜

### Dynamics — 动态

机制运行后可能出现的行为模式。

例如：

- 玩家囤积资源
- 玩家等到活动最后一天冲榜
- 玩家集中升级最高收益单位
- 玩家避开高风险路线

Dynamics 往往不是代码里直接写出来的。

### Aesthetics — 体验

玩家可能形成的体验：

- 竞争
- 成就
- 紧张
- 探索
- 表达
- 收集
- 掌控
- 成长

### 正确推理方式

```text
机制
→ 可能形成的动态
→ 可能形成的体验
→ 产品假设
→ 证据验证
```

错误：

```text
有排行榜
→ 提升留存
```

更严谨：

```text
排行榜 + 排名奖励 + 周期重置
→ 可能推动比较、重复挑战、赛季末冲榜
→ 可能强化竞争和地位体验
→ 对目标玩家是否增加回访仍是产品假设
→ 需要参与率、重复挑战行为、回访 Cohort 验证
```

## 4. 核心循环（Core Loop）

**来源基础：[S001][S002]**
**整理方式：本仓库二次整理。**

把功能写成：

```text
触发
→ 目标
→ 行为
→ 成本/风险
→ 反馈
→ 奖励/状态变化
→ 下一个目标
```

逐项检查：

### 触发

- 为什么进入？
- 玩家主动还是系统强制？
- 进入前是否知道价值？

### 目标

- 玩家知道自己要做什么吗？
- 成功标准清楚吗？

### 行为

- 玩家真正做出的选择是什么？
- 是操作、策略、资源分配、等待，还是重复执行？

### 成本/风险

- 消耗什么？
- 失败损失什么？
- 是否存在机会成本？

### 反馈

- 玩家能否理解行动后发生了什么？

### 奖励

奖励究竟提供：

- 强度
- 新选择
- 进程
- 收集
- 表达
- 社交地位
- 剧情
- 便利性

### 下一个目标

- 完成后是否自然产生下一目标？
- 下一轮是增加深度，还是完全相同的重复？

## 5. 有多个按钮，不代表有“有意义的选择”

**来源基础：[S002][S004]**
**整理方式：本仓库总结。**

检查：

- 结果是否真的不同？
- 是否存在一个几乎所有情况下都更优的选项？
- 成本是否有真实差异？
- 环境是否会改变最佳选择？
- 玩家能否在选择前理解主要后果？

常见失败：

### 假选择

看似有多个选项，但有一个明显最优。

### 不透明选择

信息不足，玩家只能猜。

### 已解选择

长期形成唯一固定解。

### 伪策略

只是 UI 上有多个入口，底层结果相同。

**注意：**

不是所有交互都必须是策略选择。

有些交互的目的可能是：

- 表达
- 节奏
- 仪式感
- 可访问性
- 情绪反馈

## 6. 正反馈与负反馈

**来源基础：[S001][S004]**
**整理方式：概念摘要。**

### Positive Feedback

领先/成功会进一步增加领先优势。

可能带来：

- 动量
- 成长感
- 更快结束比赛

风险：

- runaway leader
- 前期失误过度放大
- 比赛过早失去悬念

### Negative Feedback

落后者获得帮助，或领先者承受额外阻力。

可能带来：

- 追赶空间
- 更长悬念

风险：

- 成功被惩罚
- 故意落后成为策略
- 玩家觉得系统操纵结果

**结论边界：**

不能简单写：

> Positive Feedback = 坏
> Negative Feedback = 好

必须看目标体验和节奏。

## 7. UI 是游戏设计的一部分

**来源：[S003]**

区分：

### Input

玩家如何给系统命令。

### Output

系统如何告诉玩家：

- 当前状态
- 行为结果
- 可执行选项
- 错误原因
- 进度
- 成本
- 奖励

检查两个维度：

- **Ease of Learning**：第一次是否容易理解
- **Ease of Use**：熟悉后是否容易高频操作

### 用户模型 vs 程序模型

如果玩家认为“这里应该这样工作”，但程序实际上不同，就会出现体验问题。

Agent 不应轻易写：

> 玩家操作错了。

应该先检查：

> 是否是界面或规则表达让玩家形成了错误 mental model？

## 8. 系统不能只孤立评审

**来源基础：[S002]**
**整理方式：系统性检查规则。**

一个局部改动可能影响：

- 经济
- 成长
- 难度
- 商业化
- 活动
- 社交
- 收集
- 排行
- Matchmaking
- LiveOps

例如：

```text
提高副本奖励
→ 副本体验更爽
→ 同时可能导致金币通胀
→ 商店价格失去意义
→ 其他玩法奖励贬值
```

任何重大建议都应列出可能受影响的邻接系统。

## 9. 推荐分析流程

**来源基础：[S002][S009]**
**整理方式：Agent 工作流。**

1. 先列事实。
2. 描述规则与状态变化。
3. 识别资源与信息。
4. 还原核心循环。
5. 分析玩家可能做出的选择。
6. 分析可能出现的 Dynamics。
7. 推断可能支持的体验。
8. 对比项目明确目标。
9. 找出 mismatch。
10. 提出建议。
11. 标明风险。
12. 指定验证方式。

---

## 10. 不允许直接得出的结论

以下结论不能只根据机制或代码得出：

- 玩家喜欢这个功能
- 玩家理解这个系统
- 这个系统提升留存
- 这个系统提升付费
- 这个系统很公平
- 这个系统一定有策略深度
- 奖励足够有吸引力

这些都需要额外证据。[S011]
