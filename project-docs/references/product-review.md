# 产品与功能评审（Product Review）

## 0. 用途

用于评审一个游戏功能是否：

- 有明确用户价值
- 有完整使用路径
- 和项目核心循环一致
- 能被玩家理解
- 在首次体验和长期使用中都成立
- 与数值、经济、商业化不冲突

本文件不负责“拍脑袋想功能”，而负责结构化检查。

---

## 1. 先确定评审问题

**来源基础：[S002][S011]**
**整理方式：本仓库评审规范。**

不要问：

> 这个功能好不好？

改成：

- 新手能否理解升级循环？
- 活动是否形成完整重复循环？
- 这个礼包是否破坏免费成长结构？
- 该系统在第一次完成后是否仍有长期价值？
- 玩家进入功能前是否理解成本和目标？

---

## 2. 明确用户价值

**来源基础：[S001][S009]**

可能服务的价值：

- 成长
- 掌握
- 竞争
- 探索
- 收集
- 表达
- 社交
- 放松
- 优化
- 剧情

先找项目明确意图。

如果没有明确文档，只能写：

> 推测该功能主要试图支持……

不能写成：

> 该功能的设计目的就是……

---

## 3. 用一句话表达 Value Proposition

**整理方式：本仓库方法。**

模板：

```text
对于 [目标玩家/场景]，
该功能通过 [核心行为]，
帮助玩家获得 [价值]，
玩家需要付出 [时间/资源/风险]。
```

如果写不出来，通常说明：

- 功能价值不清
- 核心行为不清
- 目标用户不清
- 成本/回报关系不清

---

## 4. 玩家路径

**来源基础：[S002][S003]**
**整理方式：本仓库 Player Journey。**

```text
发现
→ 进入
→ 理解
→ 第一次行动
→ 得到反馈
→ 成功/失败
→ 得到奖励
→ 再次进入
→ 长期状态
```

每一步检查：

- 玩家知道下一步吗？
- 需要什么前置知识？
- 是否被资源/等级/时间阻塞？
- 是否知道为什么阻塞？
- 是否清楚奖励价值？

---

## 5. 首次体验与重复体验必须分开

**来源基础：[S003]**

### First-time

- 为什么要进入？
- 第一个动作清楚吗？
- 失败是否能理解？
- 第一份奖励是否展示系统价值？

### Repeat-use

- 第二次和第十次有什么变化？
- 是更深、更快、更策略、更丰富？
- 还是只在重复同一件事？

---

## 6. 功能闭环

**来源基础：[S002]**
**整理方式：本仓库循环模板。**

```text
触发 → 目标 → 行为 → 反馈 → 奖励 → 下一个目标
```

常见问题：

- 没有触发理由
- 目标不清楚
- 行为和目标脱节
- 反馈太弱
- 奖励没有价值
- 完成后没有下一目标
- 下一目标只是纯重复

---

## 7. 一致性检查

### 规则一致

- UI 文案
- 代码
- 配置
- 文档
- Server

是否一致？

### Mental Model 一致

**来源：[S003]**

玩家预期与系统行为是否一致？

### Progression 一致

功能的成本、奖励、门槛是否适合目标阶段？

### Economy 一致

是否向全局经济注入/抽走大量资源？

### Monetization 一致

付费是否直接破坏核心免费成长结构？

---

## 8. 区分不同产品问题

**整理方式：本仓库诊断分类。**

### Discoverability

玩家没找到。

### Comprehension

玩家找到了，但不理解。

### Value

玩家理解了，但不想用。

### Execution

玩家想用，但操作/条件阻止了他。

### Balance

玩家愿意用，但成本收益关系有问题。

不同问题不应该用同一个解决方案。

---

## 9. Intended / Implemented / Observed

**来源基础：[S011]**
**整理方式：本仓库证据框架。**

| 层 | 问题 | 证据 |
|---|---|---|
| Intended | 设计希望玩家怎么做？ | PRD / 策划案 / 决策记录 |
| Implemented | 系统实际上允许怎么做？ | Code / Config / Runtime |
| Observed | 玩家实际怎么做？ | Telemetry / Playtest |

典型诊断：

```text
Intended ≠ Implemented
→ 实现/生产问题

Implemented ≠ Observed
→ 可能是理解、价值、平衡、受众或上下文问题

Intended ≠ Observed 且 Implemented 正确
→ 原始产品假设可能不成立
```

---

## 10. 建议必须包含验证

**来源基础：[S011][S012]**

每条建议包含：

### Finding

发现什么？

### Evidence

什么证据？

### Interpretation

为什么重要？

### Recommendation

具体改什么？

### Expected Mechanism

为什么可能有效？

### Risk

会伤到哪里？

### Validation

怎样知道改对了？

---

## 11. 禁止的快捷结论

不要直接写：

- “这个功能很无聊”
- “玩家一定会喜欢”
- “加签到提升留存”
- “多发奖励提升参与”
- “竞品有，所以我们也应该有”
- “代码实现完整，所以玩家能理解”
